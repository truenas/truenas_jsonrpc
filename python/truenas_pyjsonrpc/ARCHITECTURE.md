# truenas_pyjsonrpc — architecture & integration guide

This document is the **Python implementation's** architecture & integration guide — the
component/server boundary, the session state machine, the per-request dispatch flow, the
`$/` control messages, and the contract your transport layer must satisfy — expressed
against the Python API (`JSONRPCProtocol.dispatch`, `poll_notification`, handler
signatures, …).

> The **language-agnostic protocol contract** — the same architecture without the Python
> API — is the repo-root [ARCHITECTURE.md](../../ARCHITECTURE.md). Read that for the wire
> spec every implementation follows; read this for the Python mapping.

For the *method-author* API (defining methods, writing handlers, the feature flags)
see [README.md](../README.md). The two are complementary: README = "how do I use the
library to define an API?"; this doc = "how do I run it inside a server, and how
does the protocol behave?".

## 1. Component vs server — the boundary

`truenas_pyjsonrpc` is the **dispatch core**, not a server.

| In scope (this library) | Out of scope (the server's job) |
|---|---|
| Protocol/envelope parsing + validation | Transport + framing (length-prefixed, Content-Length, newline-delimited, …) |
| The dispatch state machine | The event loop / accepting connections |
| Message construction (responses, `$/progress`, pub/sub) | The per-connection read loop |
| authz / audit / cancel / session hooks | The threads that **drain** the outbound + audit queues |
| The session lifecycle + gate | Routing an outbound message to the right socket |
| The outbound + audit queues | Connection/session registries, backpressure |

The seam is one call:

```python
response: bytes | None = protocol.dispatch(wire: bytes | str, session: SessionState)
```

bytes in → bytes out (or `None` for a notification). Everything around it — sockets,
framing, threads, routing — the server provides.

## 2. The session state machine

Every connection has exactly one **`SessionState`**, created by
`protocol.new_session(server_state=...)`. The server holds it for the connection's
lifetime and passes it to **every** `dispatch`. It is never serialized to the wire.
Its fields:

| field | meaning |
|---|---|
| `session_uuid` | unique id, generated by the protocol |
| `protocol_name` | the owning `JSONRPCProtocol(name=…, version=…)`'s `name` |
| `lifecycle` | a `SessionLifecycle` (below) |
| `server_state_internal` | opaque, **server-side** (connection handle + authenticated identity/permissions); seeded at `new_session`, typically set by a setup handler; what handlers and the `authorization_handler` read |
| `server_state_external` | opaque, **client-facing**; set to a setup handler's result |

### Lifecycle

```
new_session --> NONE --$/sessionSetup--> (INIT --$/sessionSetupContinue-->)* ESTABLISHED

{ INIT, ESTABLISHED }  --$/sessionClose | close_session()-->  CLOSED
```

| state | meaning | what's reachable |
|---|---|---|
| `NONE` | fresh, unauthenticated | `$/serverInfo`, `$/sessionSetup`, `pre_auth=True` methods (and **all** methods if no session setup is configured) |
| `INIT` | multi-step auth in progress | `$/serverInfo`, `$/sessionSetupContinue` |
| `ESTABLISHED` | authenticated | everything (normal methods, pub/sub, `$/cancelRequest`, `$/sessionClose`) |
| `CLOSED` | ended | nothing — every message is rejected with `SESSION_NOT_ESTABLISHED` |

**Transitions** are decided by what a setup handler **returns** (`(SessionLifecycle,
result)`), or by close:

| from | event | to |
|---|---|---|
| `NONE` | `$/sessionSetup` handler returns `ESTABLISHED` | `ESTABLISHED` |
| `NONE` | `$/sessionSetup` handler returns `INIT` (multi-step) | `INIT` |
| `INIT` | `$/sessionSetupContinue` returns `ESTABLISHED` | `ESTABLISHED` |
| `INIT` | `$/sessionSetupContinue` returns `INIT` (another step) | `INIT` |
| `NONE` / `INIT` | setup handler raises `JsonRpcError` (auth fail) | *unchanged* (a retry is allowed) |
| `INIT` / `ESTABLISHED` | `$/sessionClose` (client) | `CLOSED` |
| any | `protocol.close_session(session)` (server, on socket drop) | `CLOSED` |

**The gate.** When session setup is configured (`add_session_setup` was called), a
non-`pre_auth` method requires `lifecycle is ESTABLISHED`; otherwise the protocol
returns `SESSION_NOT_ESTABLISHED` (-32002). **If no session setup is configured the
gate is off** and all methods are reachable from `NONE` — mirroring "no `authorization_handler` ⇒ open".

## 3. Per-request dispatch flow

`dispatch(wire, session)` runs, per message:

1. **Parse** the envelope. Malformed JSON → `INVALID_JSON` (-32700); a valid
   non-object (incl. a top-level Array / batch) → `INVALID_REQUEST` (-32600).
2. **Resolve `id`.** Present → must be a canonical UUID string (else
   `INVALID_REQUEST`). Absent → this is a **notification** (no reply).
3. **Structural checks:** `jsonrpc == "2.0"`, `method` is a non-empty string.
4. **CLOSED short-circuit:** a closed session rejects everything.
5. **Control-message interception** (in order): `$/cancelRequest`, `$/serverInfo`,
   `$/sessionSetup`, `$/sessionSetupContinue`, `$/sessionClose` (see §4).
6. **Method lookup.** Unknown method → `METHOD_NOT_FOUND` (request) / ignored
   (notification).
7. **Subscribe id check:** a `SERVER_CLIENT` (subscribe) request must carry an `id`.
8. **Session-established gate** (§2) — only when session setup is configured.
9. **Params:** decode + validate into `accepts`; run `accepts_validator`.
10. **authorize → dispatch handler → validate `returns` → `returns_validator`.**
11. **audit** (if `method.audit` and an `audit_handler` is registered).
12. **Rebuild** the response envelope (or `None` for a notification).

A **`FilterableJSONRPCMethod`** wraps step 10: after the param decode (step 9) the
framework compiles the request's `query-filters`/`query-options` (invalid → `INVALID_PARAMS`)
and passes them to the handler as `filters`/`options`; the handler returns the narrowed
`list[entry]` (or an `int` for `count`), and the framework applies the `get` single-record
convention (no match → `REQUEST_FAILED`) before encoding. `returns` stays `None` — `entry`
carries the element type. The wire grammar is the language-agnostic
[ARCHITECTURE.md → Query methods](../../ARCHITECTURE.md#7-query-methods-filtering).

Errors never raise out of `dispatch` — every protocol/handler fault becomes a wire
error object. A handler may `raise JsonRpcError(code, message, data)` to choose the
code; any other exception becomes `INTERNAL_ERROR` (-32603).

Visually — the inbound pipeline (any step may short-circuit to an error response):

```
   wire bytes  +  SessionState (per connection)
        |
        v
   dispatch(wire, session)
        |
        v
   parse envelope -----------------> malformed / non-object  => error response
        |
        v
   resolve id (a UUID, else INVALID_REQUEST;  absent => notification, no reply)
        |
        v
   CLOSED session? ----------------> yes  => SESSION_NOT_ESTABLISHED
        |
        v
   control ($/...) message? -------> yes  => control handler (section 4)
        |     ($/cancelRequest, $/serverInfo, $/sessionSetup,
        |      $/sessionSetupContinue, $/sessionClose)
        v  no
   method lookup ------------------> unknown  => METHOD_NOT_FOUND
        |
        v
   session gate: ESTABLISHED? -----> no  => SESSION_NOT_ESTABLISHED
        |        (only when add_session_setup is configured)
        v
   decode params -> accepts Struct  (+ accepts_validator)  => INVALID_PARAMS on failure
        |
        v
   authorize(request=JSONRPCRequest, session_state[, target]) --> deny => NOT_AUTHORIZED
        |
        v
   handler(request, session_state, request_state: RequestState) -> returns Struct
        |    may: update_progress() / set_audit() / raise_if_cancelled() / raise JsonRpcError
        v
   validate returns  (+ returns_validator)
        |
        v
   audit  (when method.audit and an audit_handler is registered)  -> AuditRecord
        |
        v
   response envelope  -->  wire bytes        (or None for a notification)
```

The **outbound** (back channel) path — `$/progress` and pub/sub — is decoupled from
`dispatch`; the protocol enqueues, and the server drains on its own thread:

```
   request_state.update_progress(...)       protocol.send_notification(topic, payload)
            |                                         |  validate vs `notifies`;
            |  $/progress {id, ...}                   |  one entry per Subscription
            v                                         v
       +-------------------------------------------------+
       |   outbound queue  (one per JSONRPCProtocol)     |
       +-------------------------------------------------+
                              |
                              v
       poll_notification(block, timeout)  ->  (SessionState, wire bytes)
                              |
                              v
       server routes by session_uuid  ->  the connection's socket
```

## 4. Control messages (`$/` namespace)

`register()` rejects `rpc.`- and `$/`-prefixed names; `$/` is reserved for these.
An unknown `$/...` request → `METHOD_NOT_FOUND`; an unknown `$/...` notification →
ignored.

| message | direction | needs id | allowed lifecycle | authz | audited | purpose |
|---|---|---|---|---|---|---|
| `$/progress` | **server → client** | — | n/a | — | — | progress for an in-flight request (emitted by `request_state.update_progress`) |
| `$/serverInfo` | client → server | yes | any but `CLOSED` | **no** | **no** | unauthenticated server-identity probe (opt-in: `register_server_info`) |
| `$/sessionSetup` | client → server | yes | `NONE` | **no** (is auth) | **yes** | first auth step (opt-in: `add_session_setup`) |
| `$/sessionSetupContinue` | client → server | yes | `INIT` | **no** (is auth) | **yes** | subsequent auth step (multi-step / 2FA) |
| `$/sessionClose` | client → server | yes | `INIT`, `ESTABLISHED` | **no** (self) | **yes** | client logout → `CLOSED` |
| `$/cancelRequest` | client → server | yes | any¹ | **yes** (session-scoped) | **yes** | cancel an in-flight `cancellable` request **or** drop a subscription, by id |

¹ `$/cancelRequest` isn't lifecycle-gated, but there is nothing to cancel before
`ESTABLISHED` (no normal request in flight, no subscription), so a pre-auth cancel
resolves to `REQUEST_FAILED` ("no active request or subscription").

> **`$/negotiate` is a server-layer message, not part of this dispatch core.** It is
> handled entirely by `truenas_pyjsonrpc_server`, which holds *named* protocols and
> binds a connection to one before any dispatch happens. The dispatch core here never
> sees it. A connection's first message is `$/negotiate {protocol: "<name>"}` → the
> server replies `{protocol, server, available: [...]}` and only then creates the
> `SessionState` for the chosen protocol; the full flow is `$/negotiate →
> $/sessionSetup → API calls`. If you embed the dispatch core directly (no
> `truenas_pyjsonrpc_server`), there is no negotiation — you pick the protocol.

**`$/sessionSetup` / `$/sessionSetupContinue`** — the handler is called
`handler(request=<accepts>, session_state)` and **returns `(SessionLifecycle,
result)`**. It authenticates, sets `session_state.server_state_internal`, and the
protocol validates `result` against the method's `returns`, stores it as
`server_state_external`, sets the lifecycle, and replies. Setup **bypasses** the
`authorization_handler` but is **always audited** (credential fields marked
`SECRET` are redacted in the audit view).

**`$/cancelRequest`** — `params: {"target_id": <uuid>}`. The `target_id` is resolved
against **both** in-flight requests *and* subscriptions (request ids are client-minted;
subscription ids are server-minted — distinct UUIDs, no collision). The protocol looks
the target up, calls the `authorization_handler` with `target=<RequestState |
Subscription | None>` (so it can compare `session_state.session_uuid` to
`target.session_state.session_uuid`; both target types expose `session_state`), then:
for an in-flight **request**, sets its cancellation event and runs the optional
`register_cancellation_handler`; for a **subscription**, drops it server-side (a
wire-level unsubscribe — the `register_cancellation_handler` is not invoked). See
README → *Cancellation*.

## 5. Server integration — the contract

> **Don't want to implement this yourself?** `truenas_pyjsonrpc_server` is a turnkey
> asyncio server (AF_UNIX, TCP, and/or WebSocket; length-prefixed or WS framing; the
> `$/negotiate` front door, the executor + drain bridge, and the session registry) that
> does everything below.
> Pair it with `truenas_pyjsonrpc_client` (a thread-safe client) and generate a typed
> client with `python -m truenas_pyjsonrpc_client.codegen`. The contract below is what
> that server implements — read it if you embed the dispatch core in your own loop.

What a server MUST do to run this component:

1. **Build the protocol once, at startup.** Register methods + handlers + `name`,
   `add_session_setup(...)`, `register_server_info(...)`, etc. One
   `JSONRPCProtocol` is safe for concurrent use by many threads.

2. **One `SessionState` per connection.** On accept:
   `session = protocol.new_session(server_state=<your connection context>)`. Keep it
   for the connection; pass it to every `dispatch`.

3. **Inbound loop.** For each *framed* inbound message:
   ```python
   reply = protocol.dispatch(wire, session)
   if reply is not None:
       transport.send(reply)          # None == a notification (no reply)
   ```
   Framing is yours (the component is frame-agnostic — `bytes`/`str` in).

4. **Outbound drain thread (required for progress + pub/sub).** Run a thread:
   ```python
   while running:
       out = protocol.poll_notification(block=True, timeout=0.5)
       if out is not None:
           target_session, data = out
           route(target_session, data)     # write `data` to that session's socket
   ```
   It MUST run **concurrently** with dispatch: a request's still-queued progress is
   **purged when the request completes**, so progress is only delivered if drained
   live. `poll_notification` yields the target `SessionState`; map it to a socket
   (via `session.server_state_internal`, or your own `session_uuid → socket` table).

5. **Audit drain thread (only if `use_audit_queue=True`).**
   ```python
   while running:
       rec = protocol.poll_audit(block=True, timeout=0.5)
       if rec is not None:
           rec.run()                        # redacts + calls your audit_handler
   ```
   With `use_audit_queue=False` (default), auditing runs inline on the dispatch
   thread and no drain is needed.

6. **Publish** server→client events with `protocol.send_notification(topic,
   payload)`; the drain (step 4) delivers one copy to each subscriber.

7. **Clean up on disconnect.** On socket close call
   `protocol.close_session(session)` — it sets `CLOSED` and drops that session's
   subscriptions. **Without this, subscriptions leak.** (A client `$/sessionClose`
   does the same thing from the other side.)

### Concurrency contract

- **One protocol, many threads — safe.** The dispatch table is read-only after
  setup; the outbound queue, in-flight registry, and subscription registry are
  guarded by a single `threading.Condition`; the shared msgspec encoder/decoder are
  GIL-safe (stress-tested).
- **A connection's own messages during setup should be sequential.** `SessionState`
  is not lock-guarded; its `lifecycle`/state is mutated by the setup handler on the
  dispatch thread. Don't pipeline a single session's `$/sessionSetup*` messages.
- **Long handlers run on the dispatch thread.** For per-connection concurrency,
  dispatch on a worker pool — then a `$/cancelRequest` can arrive on another thread
  while the target runs (the intended cancellation scenario). Cancellation is
  cooperative; Python can't safely force-kill a worker thread.

## 6. Raw-fd transfer (bulk streams)

Some operations move a **bulk, self-delimiting byte stream** that shouldn't be framed
as JSON-RPC messages and copied through Python — e.g. a `zfs send`/`recv` stream driven
by libzfs (`lzc_send` / `lzc_receive`) directly on the socket. A
`JSONRPCFdTransferMethod` lends its handler **exclusive access to the connection's raw
socket fd** for the duration of one such stream, then the connection resumes normal
JSON-RPC.

It is a **two-step** method:

| step | callback | runs | returns |
|---|---|---|---|
| **negotiate** | `negotiate(request=<accepts>, session_state)` | dispatch thread (after the gate, param decode, and authz) | an interim "ready" value (any JSON) — sent to the peer as `$/transferReady.params.result`; raise `JsonRpcError` to refuse |
| **transfer** | `transfer(file_transfer: FileTransfer)` | the **executor** (it blocks) | the final `returns` Struct — validated, audited, and sent as the normal response |

`FileTransfer.fileno()` is the point of it — hand that (blocking) fd to libzfs,
`os.sendfile`, `splice`, etc. `.params`, `.session_state`, `.direction`, and `.result`
(the interim value `negotiate` returned — the producer's channel to tell the consumer
about the stream, e.g. a server `DOWNLOAD` reporting the byte count the client reads as
`ft.result["size"]`) are also on it; `sendfile()` / `recvfile()` are convenience helpers
for the plain-file case.
`TransferDirection` names who **produces** the stream: `DOWNLOAD` — the server produces,
the client consumes; `UPLOAD` — the client produces, the server consumes.

### Dispatch integration

A transfer method does **not** return wire bytes from `dispatch`. When `_dispatch_one`
sees a `JSONRPCFdTransferMethod` it runs the gate + param decode + authz, calls
`negotiate`, and returns a **`Transfer` directive** instead of a response dict — so
`dispatch()`'s return type widens to `bytes | None | Transfer`. The server detects the
`Transfer`, drives the wire handshake, builds a concrete `FileTransfer` over the
connection's fd, and calls `Transfer.complete(file_transfer)` (which runs `transfer`,
validates `returns`, audits, and returns the final response envelope to send). The
dispatch core itself never touches a socket — `FileTransfer` is abstract here; the
concrete fd-backed impl lives in the server/client.

### The wire handshake — `$/transferReady` / `$/transferGo`

These are server-layer control messages (correlated by the request id, like
`$/progress`). The **invariant**: the *consumer* must pause its reader before the
*producer* writes a stream byte, so every byte lands in the kernel buffer the
fd-owning callback reads from — the framing layer's userspace buffer is bypassed
(libzfs reads the fd directly and can't see bytes buffered there).

```
UPLOAD  (client produces, server consumes)          DOWNLOAD (server produces, client consumes)

  C--> request {id, method, params}                 C--> request {id, method, params}
  S: negotiate -> ready                             S: negotiate -> ready
  S: pause reader   (consumer first)                S--> $/transferReady {id, result}
  S--> $/transferReady {id, result}                 C: pause reader   (consumer first)
  C--> [ raw stream ]   lzc_send(fd)                C--> $/transferGo {id}
  S: transfer cb reads fd  lzc_receive(fd)          S--> [ raw stream ]   lzc_send(fd)
  S--> response {id, result}                        C: transfer cb reads fd  lzc_receive(fd)
                                                    S--> response {id, result}
```

While the transfer callback runs, the connection's reader is paused, its writer is
suspended, and the fd is set **blocking**; all three are restored afterwards, so a
normal `call()` round-trips on the same connection once the transfer completes. The
stream is self-delimiting — the framework imposes no length; the callback (libzfs)
returns when the stream is done.

### Encryption — plain or kTLS only

The handler reads/writes **plaintext** on the fd, so the fd must carry plaintext on the
wire **or** be transparently encrypted by the kernel:

- **Plain** transports (AF_UNIX, plain TCP) — no encryption.
- **kTLS** (kernel TLS) — set `ctx.options |= ssl.OP_ENABLE_KTLS` on the server's *and*
  client's `SSLContext`. The handshake runs on the real fd and the kernel does the
  record crypto, so `read` / `write` / `sendfile` on the fd are plaintext while the wire
  is encrypted. Requires an AES-GCM/ChaCha20 cipher; the server **must** set
  `ctx.num_tickets = 0` (TLS 1.3 post-handshake session tickets are non-data records a
  raw `recv` can't decode → the peer's kTLS RX fails with `EIO`) — the server sets this
  automatically. If kTLS can't engage, the handshake fails **loudly** rather than
  silently leaving ciphertext on the fd.
- **asyncio `ssl=` without kTLS** (the default memory-BIO TLS) puts **ciphertext** on
  the fd — a transfer over such a connection is **rejected** with `REQUEST_FAILED`.

See the [server README](../truenas_pyjsonrpc_server/README.md#raw-fd-transfers-sendfilerecvfile)
(defining a transfer method, kTLS setup) and the
[client README](../truenas_pyjsonrpc_client/README.md#raw-fd-transfers) (driving one).

## 7. Callback signatures (reference)

All hooks are called **by keyword**; handlers may use `**kwargs`.

| hook | signature | returns |
|---|---|---|
| method handler | `handler(request=<accepts>, session_state, request_state)` | `<returns>` (or raise `JsonRpcError`) |
| filterable handler | `handler(request=<accepts>, session_state, request_state, filters, options)` | `list[entry]` (or `int` for `count`); framework then applies `get` |
| `authorization_handler` | `(request=JSONRPCRequest, session_state[, target=RequestState\|Subscription\|None])` | `AuthorizationResponse` |
| `audit_handler` | `(request=JSONRPCRequest, response=dict, session_state, audit_message=str\|None)` | ignored |
| `cancellation_handler` | `(request=JSONRPCRequest, target=RequestState, session_state)` | ignored |
| server-info handler | `(session_state)` | the registered `returns` Struct |
| session-setup handler | `(request=<accepts>, session_state)` | `(SessionLifecycle, <returns>)` |

`target` is passed to `authorization_handler` **only** for `$/cancelRequest`.

## 8. Error codes (reference)

All in the `JSONRPCError` `IntEnum` (members compare/serialize as their `int`).

| name | code | meaning |
|---|---|---|
| `INVALID_JSON` | -32700 | malformed JSON ("Parse error") |
| `INVALID_REQUEST` | -32600 | bad envelope (incl. non-UUID id, top-level Array) |
| `METHOD_NOT_FOUND` | -32601 | unknown method |
| `INVALID_PARAMS` | -32602 | params failed decode/validation (by-name only) |
| `INTERNAL_ERROR` | -32603 | unexpected handler/return fault |
| `NOT_AUTHORIZED` | -32000 | `authorization_handler` denied (library code) |
| `SESSION_NOT_ESTABLISHED` | -32002 | normal method before `ESTABLISHED`, or on `CLOSED` (LSP-derived) |
| `REQUEST_CANCELLED` | -32800 | request cancelled via `$/cancelRequest` (LSP-derived) |
| `REQUEST_FAILED` | -32803 | valid+authorized request failed for an expected reason; vs `INTERNAL_ERROR` = bug (LSP-derived) |

## 9. Deliberate divergences from JSON-RPC 2.0

- **No batch** — top-level Arrays are `INVALID_REQUEST`.
- **UUID-only ids** — a present `id` must be a canonical UUID string.
- **By-name params only** — `params` must be a JSON object (no positional arrays).
- **Reserved namespaces** — `rpc.` and `$/` can't be registered.
